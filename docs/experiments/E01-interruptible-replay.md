# E01. interruptible: оценка повторным прогоном истории

Дата: 09.11.2026 (пересчитано в тот же день, см. «Исправление»). Снимок: `data/snapshots/20261109`.
Воспроизвести: `python -m runners report` → раздел «Что если», показатели `whatif.*` в `out/metrics.json`.

## Условия

- Ни один репозиторий не менялся. Эксперимент — это replay истории GitLab за 30 дней (29 проектов в охвате токена) с источником каждого пайплайна (`gitlab_pipelines.csv.gz`).
- Политика: когда на той же ветке проекта создан новый пайплайн от push или MR, задания старого пайплайна останавливаются, включая запущенные. Пайплайны по расписанию, из API и из веб-интерфейса не вытесняют другие и сами не вытесняются.

## Исправление

Первая версия E01 дала 13,1%. Это завышение: replay считал, что пайплайны по расписанию на `main` вытесняют друг друга. В santinel 1 667 из 1 997 пайплайнов `main` — это расписания (бэкапы, карта тестов), и проект намеренно защищает их правилом `auto_cancel: on_new_commit: none`. С учётом источника пайплайна оценка 5,7%.

## Что уже сделано в santinel (по его `.gitlab-ci.yml`, только чтение)

- `default: interruptible: true`. Задания с `interruptible: false` — только выкатка, бэкапы, карта тестов и операции.
- В MR включён `auto_cancel: on_job_failure: all`: первое упавшее задание снимает весь пайплайн.
- Draft-MR гоняют только линтеры. Есть merge train: стадия test на `main` не перегоняется, если поезд уже проверил этот sha.

Значит, santinel уже применил то, что E01 собирался предложить. Остаток экономии в нём (122 ч на MR-ветках) — это пайплайны, которые по конфигу должны были отмениться, но не отменились. Возможная причина — настройка проекта «Auto-cancel redundant pipelines» (её значение по API токену не видно) или режим `conservative`, если в пайплайне стартовало ручное задание с `interruptible: false` (`build:stage-image`). Это нужно проверить в настройках проекта.

## Результат

Прямой replay (не зависит от модели очереди), показатели `whatif.*`:

| Что прерываем | Доля времени раннеров |
|---|---|
| Все задания, кроме выкатки (`whatif.interruptible_saved_pct`) | **5,7%** (240 ч за 30 дней) |
| Все задания (`whatif.interruptible_all_pct`) | 5,8% |
| Все, кроме веток main/master (`whatif.interruptible_no_main_pct`) | 4,1% |

Кроме santinel (137 ч), заметная доля в `ai-hackathon-summer-2026/hachathon-2/agent` (48 ч) и `sip-service/sip-service-poc` (27 ч). У них `interruptible` по конфигу, вероятно, не включён — это не проверялось.

Модель очереди (FIFO, K одинаковых слотов, K откалиброван по фактическому p95) — значения в `whatif.sim_*` и в разделе отчёта. Сравнивать нужно варианты модели между собой, а не с фактом.

## Ограничения

- Модель очереди грубая: один пул без тегов; стадии не сдвигаются, если предыдущие закончились раньше; проекты вне охвата GitLab учтены только через калибровку K.
- Класс «выкатка» определяется по имени задания.
- Не учтено, что агент, получив результат быстрее, может пушить чаще.

## Вывод для доклада

Самый нагруженный проект уже сам, руками агентов, включил прерываемость, автоотмену по первому падению, Draft-only-lint и merge train. Повторный прогон истории показывает, что по всему охвату остаётся около 6% времени раннеров. Политика отмены — не главный рычаг. Главный, судя по E00 и разделу cgroup, — ресурсы задания и размер пиков.
