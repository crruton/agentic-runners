# E09. Выбор тестов по выполненному коду: обход связности через conftest

Дата: 11.11.2026. Гипотеза H4. Основание — E08: корневой `tests/conftest.py` santinel импортирует 514 из 521 модуля приложения, поэтому выбор по импортам упирается в потолок (коммиту агента нужно в среднем 45,5% тестового времени).

## Что сделано

`--rt-select=coverage` в рантайме (вместе с `--rt-cache`). Ключ файла тестов строится из:

- замыкания импортов самого файла теста (ловит константы и данные, импортированные напрямую);
- содержимого цепочки `conftest.py` — без их замыкания импортов;
- файлов проекта, код которых **выполнялся** в тестах этого файла в прошлом полностью успешном прогоне;
- файлов, выполнявшихся на этапе setup фикстур в любом тесте сессии: сессионные фикстуры создаются один раз, их код входит в ключ каждого файла;
- lock- и конфиг-файлов проекта.

Карта выполненного кода записывается профайлером вызовов (`sys.setprofile`, только события `call`; Python 3.11 у santinel не имеет `sys.monitoring`). Карта пишется только для файлов, прошедших целиком и без падений. В режиме форка каждый воркер пишет свою часть, при чтении части объединяются.

## Проверка правил (`runtime/tests`, Linux, 17 тестов)

Синтетический проект повторяет santinel: корневой conftest импортирует все модули, сессионная фикстура вызывает слой БД.

| Изменение | Статический ключ | Ключ по выполненному коду |
|---|---|---|
| Модуль, который выполняет только `test_1` | 3 файла из 3 | **1 файл** |
| Константа, импортированная `test_c` напрямую | — | 1 файл |
| Код сессионной фикстуры (`app/db.py`) | — | 3 файла из 3 (как и должно быть) |

То же в режиме форка: изменение модуля одного файла — 1 файл из 3.

## Цена записи

Демо-набор E04, 192 теста, 4 воркера-форка, слот 4 CPU / 4 GiB, прогон с пустым кэшем:

| Прогон | Время (два повтора) |
|---|---|
| Статический ключ | 5,5 и 5,9 с |
| С записью выполненного кода | 8,3 и 7,6 с |

Запись через `setprofile` (Python 3.11) стоит около +40% времени выполнения на файлах, которые реально выполняются. Демо-набор — худший случай: тесты целиком из Python-кода с генераторами. У тестов, ждущих БД, доля ниже.

### Python 3.12+: sys.monitoring

На Python 3.12+ запись идёт через `sys.monitoring` (событие `PY_START`): функция записывается при первом вызове и сразу отключается, в начале каждого теста события включаются заново. Если идентификатор инструмента занят (например, coverage.py), рантайм возвращается к `setprofile`.

Тот же демо-набор, образ на Python 3.13 (11.11.2026), время pytest:

| Прогон | Время pytest (два повтора) |
|---|---|
| Статический ключ | 5,65 и 6,16 с |
| С записью через `sys.monitoring` | 6,39 и 6,65 с |

Цена записи — около +8…13% вместо +40% у `setprofile` на 3.11. Тесты рантайма на Linux с Python 3.13 — 18 из 18.

## Ограничения

- Эффект на santinel не измерен: для карты нужен прогон его тестов (Postgres, Redis, около часа CPU на полный набор). Это следующий шаг пилота.
- Код, выполненный при импорте модуля (конфигурация на уровне модуля), учитывается только через замыкание импортов самого файла теста, но не через conftest. Изменение модульного кода, который тест использует лишь косвенно через conftest, ключ не увидит. Для таких проектов остаётся статический режим или явные `--rt-cache-extra`.
