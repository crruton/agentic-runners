# Scion: что это и что проверяем

Под именем Scion есть два разных подхода. Факты взяты из README и документации на 09.11.2026.

## Google Scion — оркестрация агентов

- Ссылки: https://googlecloudplatform.github.io/scion/overview/, https://github.com/GoogleCloudPlatform/scion
- Hub — control plane: идентичность, состояние, диспетчеризация.
- Runtime Broker поднимает контейнер на агента через Docker, Podman, Apple Container или Kubernetes.
- Рабочее пространство: общие каталоги, git worktree или отдельные клоны.
- Лицензия Apache-2.0, версия до 1.0.
- Документация не описывает лимиты CPU и памяти на агента.

Гипотеза: изолирует агентов, но не уменьшает стоимость CI-заданий, которые агент запускает.

## Scion-VCS — контроль версий для агентов и CI

- Основа: публичный пост Anthropic «Redesigning source control» о внутренней системе.
- https://github.com/CarterT27/scion — Rust, независимая реализация. Нужны CockroachDB, S3, TLS, ключ Ed25519. На узле работает демон с общим кэшем для заданий.
- https://github.com/tinyhumansai/openscion — Rust, GPL-3.0. Уровни: CLI, демон на узле, региональный кэш, сервер. Может работать на одном узле с SQLite.
- Идея: история на сервере, клиент забирает только нужные пути, нет клонов целиком.

Гипотеза: убирает стоимость clone и fetch, но это малая доля CPU-time заданий. Миграция с git слишком дорога для нашей задачи.

## Что измерить

- Доля времени clone, fetch и checkout в заданиях (шаг 1–3).
- Overhead контейнера на агента в модели Google Scion: старт, RSS, I/O.
- Стоимость внедрения каждого подхода в часах и инфраструктуре.
