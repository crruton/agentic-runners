# План проекта: раннеры под агентной нагрузкой

Цель: за две недели получить измеренные результаты оптимизации 9 CI-раннеров и материал для доклада на RULKC Conf 2026.

## Ключевые даты

| Дата | Событие |
|---|---|
| 10.11.2026 | Подать заявку (`docs/cfp/application.md`) |
| 10–23.11.2026 | Работа: шаги 0–9 |
| 24–30.11.2026 | Слайды, прогон доклада, правка аннотации реальными цифрами |
| 01.12.2026 | Дедлайн приёма заявок |
| 07.12.2026 | Выступление |

## Принципы

- Меряем до того, как меняем. Нет базовой линии — нет изменения (ADR-0001).
- Одно изменение за раз, A/B на подмножестве раннеров. Иначе эффект не разделить.
- Любой результат записываем в `docs/experiments/`, включая неудачи.
- Числа в докладе берутся только из журнала экспериментов.

## Шаги

### Шаг 0. Инвентаризация (10.11)

Собрать факты о парке в `docs/research/inventory.md`:

- CI-платформа, версия, executor (docker, shell, k8s), конфиг раннеров (`concurrent`, `limit`).
- Железо каждого раннера: CPU (модель, ядра, NUMA), RAM, диски, GPU.
- Ядро, дистрибутив, cgroups v1 или v2, container runtime.
- Список проектов и пайплайнов, которые гоняют агенты.

Готово, когда: таблица по всем 9 раннерам заполнена.

### Шаг 1. Базовая линия из истории CI (10–11.11)

Скрипт `collect/ci_history` выгружает задания за 60 дней через API CI.

- Метрики: время в очереди, длительность, статус, раннер, стадия, автор (агент или человек).
- Разметка агентов: бот-аккаунты, ветки, метки коммитов (`Co-Authored-By`).
- Графики: запуски в сутки агентов против людей, p50/p95 очереди и длительности по неделям.

Готово, когда: есть графики «как было» и доля нагрузки от агентов.

### Шаг 2. Системная телеметрия (11–12.11)

- node_exporter с PSI (`/proc/pressure/{cpu,memory,io}`) на всех раннерах.
- Статистика cgroup на каждое задание: `cpu.stat`, `memory.peak`, `io.stat`.
- Prometheus и Grafana с дашбордом «раннер» и «класс задания».

Готово, когда: по любому заданию видны CPU-time, пик памяти и I/O.

### Шаг 3. Классификация и профилирование (12–14.11)

- Разбить задания на классы: lint, unit, build, browser-e2e, integration-DB, deps-install.
- Для каждого класса: CPU-time, wall-time, пик RSS, I/O, доля в общем бюджете.
- В пиковые часы снять `perf sched`, bpftrace `runqlat`, `biolatency`, `offcputime`.
- Найти взаимное влияние: какие пары заданий на одном раннере замедляют друг друга.

Готово, когда: ранжированный список узких мест с цифрами в `docs/experiments/E00-diagnosis.md`.

### Шаг 4. Разбор Scion (13–15.11)

Два разных подхода с одним именем, разбираем оба (`docs/research/scion.md`):

- Google Scion: Hub, Runtime Broker, контейнер на агента. Проверить: снижает ли это стоимость CI-заданий или только изолирует агентов.
- Scion-VCS (CarterT27/scion, tinyhumansai/openscion): серверная история, разреженная выборка, кэш-демон на узле. Проверить: какая доля времени заданий уходит на clone и fetch. Оценить стоимость инфраструктуры (CockroachDB, S3, TLS).
- Замер на нашей нагрузке: доля clone и fetch в заданиях, overhead контейнера на агента.

Готово, когда: таблица «что решает, что не решает, сколько стоит» с нашими цифрами.

### Шаг 5. Дисциплина агентов (14–17.11)

Изменения на стороне агентов и пайплайнов, без изменения железа:

- Отмена устаревших пайплайнов (`interruptible`, auto-cancel redundant).
- Правила по изменённым путям (`rules: changes`): только затронутые проверки.
- MAH: skill «целевые тесты» и барьер `ask` на полный прогон (уже есть в guard).
- MAH: учёт лишних прогонов как ошибки, чтобы харнес превращал повторы в барьеры.

Готово, когда: число прогонов на задачу агента до и после, без роста пропущенных регрессий.

### Шаг 6. Хранилище и подготовка окружения (16–19.11)

- Общий кэш зависимостей на узле: npm, pip, cargo, браузеры Playwright.
- СУБД на tmpfs с `fsync=off`; шаблонная БД вместо миграций на каждый тест.
- Предсобранные образы с зависимостями.

Готово, когда: I/O wait и время подготовки задания до и после.

### Шаг 7. cgroups v2 и планировщик (18–21.11)

- Профили по классам: `cpu.weight`, `cpu.max`, `memory.high`, `io.max`.
- Ограничение параллелизма тяжёлых классов на узел.
- Опционально: привязка тяжёлых сборок к ядрам, если это даст эффект в A/B.

Готово, когда: p95 и PSI до и после на A/B-раннерах.

### Шаг 8. Пулы раннеров (20–22.11)

- Разделить парк по профилю: тяжёлые CPU-задания, лёгкие, браузерные, GPU (если есть).
- Маршрутизация через теги и правила пайплайна.

Готово, когда: очередь и утилизация пулов до и после.

### Шаг 9. Сводка (22–23.11)

- Итоговая таблица по всем экспериментам.
- Раздел «что не сработало».
- Обновить аннотацию в форме реальными цифрами, если форма позволяет правку.

## Метрики

| Метрика | Источник |
|---|---|
| Время в очереди p50/p95 | API CI |
| Длительность пайплайна p50/p95 | API CI |
| Прогонов на задачу агента | API CI + разметка |
| CPU-time на задание | cgroup `cpu.stat` |
| PSI cpu/memory/io | `/proc/pressure` |
| I/O wait, латентность диска | node_exporter, biolatency |
| Задержка в runqueue | bpftrace runqlat |

## Риски

| Риск | Что делаем |
|---|---|
| Изменения ломают и так перегруженный CI | A/B на 1–2 раннерах, быстрый откат |
| Мало данных за 2 недели | Базовая линия из истории CI за 60 дней |
| Эффект не разделить | Одно изменение за раз, журнал экспериментов |
| Нет GPU в парке | Пункт про GPU убрать из слайдов, оставить как вывод |
| Результат хуже ожиданий | Говорим об этом честно, это тоже материал |
